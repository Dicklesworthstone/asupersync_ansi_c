# C Refinement Map: asupersync v4 Formal Semantics to asx

This document maps each rule of the **Canonical Rule Index** in asupersync's
normative semantics to the C port. It follows Rust's own map
(`formal/impl_refinement_map.md`). Each row gives the rule's spec section, its
Rust anchor, the C code that implements it, the C ghost check, the C tests,
the Rust-captured fixtures that exercise it, a status, and notes. Bead:
`bd-9kll.2.12`.

**What a fixture can show.** Canonical vocabulary v2
([`docs/CANONICAL_VOCABULARY_V2.md`](CANONICAL_VOCABULARY_V2.md) §3) has no
task-state, Draining or Finalizing events. Intermediate task and region states
are visible only when they are the end state in the snapshot. So a fixture
"exercises" a rule when the rule fires in the scenario and everything the
oracle observes matches Rust. It does not mean that every intermediate state
was compared.

## Status definitions

| Status | Meaning |
|---|---|
| Implemented | C code realizes the rule, and there is evidence: a Rust-captured fixture that passes and exercises the rule, or a C test that checks the exact behaviour against Rust's definition. Some rules have two C surfaces: task groups versus the poll-based combinators of `src/core/combinator.c`, or `asx_timeout_poll`. In that case the status rates the surface the fixtures exercise, and the notes name the drift in the other surface. |
| Variant | C realizes the rule in a different shape from the spec text, usually the shape of Rust's implementation. The notes give the evidence and the difference. |
| Partial | Some preconditions or postconditions are not implemented or have no evidence. The notes say which. |
| Missing | No C mechanism enforces the rule. |

An open bead is named only where reading the current code confirmed the drift
it describes. Many bridge beads date from the 2026-10-08 audit, and parts of
them are already fixed.

## How to check and regenerate

- **Check:** `bash tools/ci/check_refinement_map.sh [docs/C_REFINEMENT_MAP.md] [schemas/v4_rule_index.json]`.
  The check fails in any of these cases:
  - a rule in the index has no row, has more than one row, or a row names an unknown rule;
  - a status is not one of the four above;
  - an `Implemented` row cites no existing fixture or test;
  - a non-`Implemented` row has no notes;
  - a cited fixture is missing from `fixtures/rust_reference_v2/`;
  - a cited test `file.c::name` does not exist;
  - a cited `path:line` is past the end of its file;
  - the status counts disagree with the `status-counts` comment above;
  - a scenario tag is not an index rule, or `scenario_tag` disagrees with the tags
    `tests/conformance/scenarios_v2/*.json` actually use.

  When an asupersync checkout with `5e60b1c4c` is present (`ASUPERSYNC_REPO`,
  default `/dp/asupersync`), the check also compares the index with the spec's
  Canonical Rule Index.
- **Regenerate the index:** extract the IDs from the spec with
  `git -C /dp/asupersync show 5e60b1c4c:asupersync_v4_formal_semantics.md | sed -n '/^### Canonical Rule Index/,/^---/p' | grep -oE '^- .[a-z_.]+. \(#[0-9]+\)'`.
  Keep `name` and `number` exactly as the spec writes them. Set `section` and
  `construct` from the spec body, and `kind` from the ID prefix (`rule`,
  `inv`, `def`, `prog`, `comb`, `law`). The script checks `scenario_tag`.
- **When code moves:** re-read each anchor and update the C commit above. A
  status may change only with new fixture or test evidence.

**Column legend.**
- **Fixtures** lists Rust-captured fixtures (`fixtures/rust_reference_v2/<id>.json`)
  whose scenario `rules[]` tags the rule.
- A starred entry, `` `id`* ``, was checked by reading the fixture and is not
  tagged.
- Every tagged scenario has a Rust capture. A row lists a representative
  subset when many fixtures tag its rule (the `supervision-*` fixtures tag
  `rule.ownership.spawn`, `def.outcome.four_valued` and often
  `rule.cancel.request`).
- **Tests** cites `file::TEST name`.

## Index entries that do not map cleanly

- **#44 `inv.capability.no_ambient` and #45 `def.capability.cx_scope`** have no
  section in the spec body; §9.1 only names `NoAmbientAuthority`. Rust's own
  `docs/semantic_docs_rule_mapping.md` reports them as 0/2 covered by the formal
  semantics: they are enforced by the Rust type system (ADR-006). The rows above
  rate them against the contract clauses in `docs/semantic_contract_invariants.md`.
- **#41 `law.race.never_abandon`.** Rust's `docs/semantic_docs_rule_mapping.md`
  maps two different things to #41: §4.2's "losers are always drained, never
  abandoned", and LAW-RACE-NEVER (`race(f, never) ≃ f`). The contract
  (`docs/semantic_contract_invariants.md`) defines #41 as "a race never leaves a
  loser Running", and the row above uses that definition. Neither engine tests
  LAW-RACE-NEVER in this oracle.
- **#33 `inv.ownership.single_owner`** has no invariant of its own in §5. The
  spec states it through `TaskRecord.region` (§2.2, a single `RegionId`).
  Rust's docs mapping ties it to the §8 `no_task_leaks` oracle.
- **#11 and #12** both come from §5 INV-MASK-BOUNDED ("finite and monotone").
  Rust's docs mapping also lists INV-DEADLINE-MONOTONE under #11. That is a slip
  in that table: deadline monotonicity has no ID in the index, and it is mapped
  in the supplementary table above.
